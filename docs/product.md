# 产品定义

> 这份文档是"我们到底在做什么"的唯一解释。后续功能取舍都以此为准。

## 一句话

**把 DeepSeek 装进一个专属 QQ 小号，让这个号成为它的"家"。**
用户像平时一样用这个号加好友、进群；AI 住在这个号里，替他回消息。

## 部署形态（已定，不再摇摆）

| 用户类型 | 形态 | 谁负责服务器 |
|---|---|---|
| 普通用户 | 双击启动，电脑常开 | 用户自己的电脑 |
| 技术人员 | Docker 部署 | 用户自己的服务器 |

**我们不做托管。** 不碰账号、不碰服务器、不代付 token。

三条理由：

1. **合规**：托管别人的 QQ 账号，责任全在你身上
2. **成本**：每个用户一台机器，免费模式养不起
3. **售后**：QQ 一更新就集体故障，你会被拖死

代价也要写清楚：**普通用户关机，机器人就离线。** 这是用"随时在线"换"轻装上阵"，
对引流阶段是划算的——先让人用起来，再谈 7×24。

## 三个角色

| 角色 | 职责 |
|---|---|
| **用户** | 拥有那个小号。手动加好友、进群、拉人。设置人格、Key、回复范围 |
| **软件** | 配置 + 管理 + 运行：登录态、消息收发、记忆、用量、日志 |
| **DeepSeek** | 只负责"说什么" |

## 核心概念：一个号 = 一个"家"

- 一个 QQ 号对应**一份人设、一份记忆、一份权限**，三者绑定，不可串
- 换号 = 换人，新号不认识旧号聊过的人
- 多号 = 多个互不相干的"人"，各自独立

这是整个数据模型的根基：所有配置和记忆都以「号」为第一维度，群和联系人只是它里面的二级维度。

## 用户和 AI 共用同一个号

这是最容易做错的地方。用户随时会拿起这个号去加人、发消息、看群，
AI 不能抢占、不能顶号、不能把用户的号挤下线。

推论：
- **不能做"协议登录"**（会顶掉官方客户端，用户就没法操作了）
- 只能做**旁路**：注入已登录的客户端，或者旁听/操作已有的界面
- 用户手动发出的消息，AI 要能识别"这不是我发的"，不要当成自己的话接

## 软件做什么

1. **配置**：API Key、人设、回复范围、触发规则、每日预算
2. **管理**：登录状态、掉线重连、好友/群列表、对话记录、用量统计
3. **运行**：收消息 → 判断要不要回 → 生成 → 回

## 软件不做什么

- 不代替用户加好友、进群（这是用户手动的事）
- 不做公共机器人广场、不做"来用我的机器人"
- 不托管用户的 QQ 账号密码

## 已定的产品决策

| 问题 | 决定 |
|---|---|
| 跑在哪 | **双端都要**：手机（用户和 AI 共用账号）+ 电脑（稳定宿主） |
| 管几个号 | **多号**：一个软件管多个小号，每个号独立人格、独立记忆，可切换 |
| 私聊 | **默认全部自动回复**，可收紧成白名单 |
| 群聊 | **可以不等 @ 自己插话**（不是每句都接，是判断后接） |

### 一条硬约束（平台决定的，不是实现问题）

**"不等 @ 就插话"必须能读到群里的全部消息。**

| 通道 | 能读全量消息吗 | 能插话吗 |
|---|---|---|
| 电脑注入（NapCat / SnowLuma） | ✅ 账号是普通群成员，能看到所有消息 | ✅ |
| QQ 官方机器人 | ✅ 群主授予"接收全量消息" | ✅ |
| 手机通知监听 | ❌ QQ 默认只在被 @ 时推通知 | ❌ |
| 手机无障碍读屏 | ⚠️ 只在 QQ 打开且停在该群时 | ⚠️ 不可持续 |

所以：**手机端做「私聊 + 被 @ 回复」，电脑端做「群里自己插话」。** 这个分工是技术现实，不是取舍。

## 插话怎么判断（当前实现）

没有语义理解，只有启发式打分，够用且可控：

| 信号 | 加分 |
|---|---|
| 问句（？） | +0.6 |
| 命中话题词 | +0.9 |
| 够长（≥12 字） | +0.2 |
| @全体成员 | +0.5 |
| 随机冲动 | 0 ~ 0.6 |

达到 0.9 才开口。所以「问句 + 话题词」必接，「只有问号」不接，「随便一句」不接。
再叠加原有的冷却时间、单用户每小时配额、免打扰时段——四道闸门防止刷屏。

> 想更聪明，可以让模型先做一次"要不要接"的判断，但每条消息都要多一次调用，成本翻倍。现在先不做。

## 权限边界（重要）

"它有没有这个号的所有权限"，要分三层看：

| 层 | 实际情况 |
|---|---|
| **① 账号在 QQ 里的权限** | 和真人**完全一样**。群主就能踢人禁言，普通成员就不能。QQ 不知道对面是人还是 AI |
| **② 宿主暴露的协议能力** | NapCat / OneBot 覆盖大部分：发消息、撤回、戳一戳、群管理、加好友、群文件……但不是全部，且各实现覆盖度不同 |
| **③ 我们软件实际调用的** | **只有「收消息 + 发消息 + 列群」**。其余接口一个都没接 |

### 我们的红线（即使技术上能做到）

| 不做 | 原因 |
|---|---|
| 踢人、禁言、改群名片 | AI 误判一次，后果由号主承担，而且撤回不了 |
| 加好友、拉群、群发 | 高风控行为，最容易触发封号 |
| 支付、红包、转账 | 涉及钱，坚决不碰 |
| 改密码、换绑手机 | 账号安全，不该由程序代劳 |
| 自动同意好友申请 | 会被用来批量加人，号很容易废 |

### 做不到的（不是因为不想做）

- 需要人工验证的操作：登录、扫码、短信验证
- 被腾讯风控拦截的操作：短时间大量加好友、异地登录
- 面板里的东西：QQ 钱包、会员、设置项——协议层没有对应接口

### 设计原则：最小权限

**即使用户的小号是群主，软件也不调用管理接口。**
AI 的职责只有一件事：说话。让它有踢人权，等于给一个会误判的东西发了一把刀。

## 双端策略：不是二选一，是能力分级

同一个号，宿主可以换。配置、人设、记忆格式完全通用，换端不用重配。

| 能力 | 电脑宿主（NapCat） | 手机宿主（APK） |
|---|---|---|
| 好友私聊自动回复 | ✅ | ✅ |
| 群聊被 @ 时回复 | ✅ | ✅ |
| 群聊不等 @ 自己插话 | ✅ | ❌ 拿不到全量消息 |
| 主动定时发消息 | ✅ | ⚠️ 要无障碍 |
| 读群成员列表 | ✅ | ❌ |
| 用户同时能操作这个号 | ✅（手机+电脑可同时在线） | ✅（就是同一台手机） |
| 要求 | 一台常开的电脑 | 开无障碍 + 保持 QQ 在后台 |
| 稳定性 | 高 | 中（控件适配、后台被杀） |

**结论：手机端保留，但少一项"群聊插话"。** 其余功能对齐。

## 落地顺序（重要）

先做电脑端，后做手机端。理由不是"手机不重要"，而是：

1. 电脑端能力完整，能先验证"这个 AI 在群里到底好不好用"——这是产品的生死问题
2. 手机端的运行时是另一套技术（Java + 无障碍），现在做等于在没验证需求时先付最贵的成本
3. 配置格式、人设、触发规则是跨端的，**先做电脑端不会让手机端白做**

### 阶段划分

| 阶段 | 内容 | 产出 |
|---|---|---|
| P1 | 电脑端 + 配置向导（加号、扫码、填 Key、选群） | 能发给朋友装的 Windows 包 |
| P2 | 跑一批真实群，调人设和插话阈值 | 知道"像不像人" |
| P3 | 手机端宿主（私聊 + @ 回复） | APK |
| P4 | 手机管理端（连电脑宿主，看状态改配置） | 手机用户也有入口 |

> P4 是个便宜的过渡：纯手机用户虽然不能自己跑宿主，但能远程管一台电脑上的号。
> 如果 P2 证明需求很强，再投入 P3 那套昂贵的无障碍方案。
